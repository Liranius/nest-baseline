# 共享设备 API 验收

## 阶段 0–1

2026-11-19 使用独立本地仓库、Node 24.22.2、pnpm 12.4.2 和 WSL Ubuntu 中的 PostgreSQL 18 容器执行。每阶段使用一个新数据库、两个实际 API 进程和公开 HTTP 客户端。

| 场景             | 核对结果                                                                                                                                            |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 空库初始化与身份 | 首次迁移应用一次，再次执行为零。重复种子后为两个组织、三个账号、两台设备。三个账号成功登录，跨实例令牌可用。错误密码、缺失和过期令牌均返回 401。    |
| 空闲查询         | 无预约返回整个窗口，时段中间已有预约则返回两段，完全占用返回空数组。等价时区输入结果一致；不同组织只收到空闲边界。                                  |
| 并发占用         | 两个客户端先看到相同时段空闲，再向不同实例并发写入。同设备重叠时段返回一个 201 和一个 409，数据库仅一笔有效预约。相邻时段及其他设备可订。           |
| 幂等与重试       | 同一员工相同键的并发重试返回同一 ID。改变时段返回 409，原时段保持有效。代理收到创建成功后丢弃响应，客户端向另一实例重试，数据库仍只有原记录。       |
| 权限与取消       | 跨组织查询和取消与不存在的记录同为 404。管理员写入为 403。重复取消均为 204；另一员工可重新预订，原键重放仍对应已取消的预约。                        |
| 契约及运行环境   | 真实客户端响应按版本化 OpenAPI 文档验证。GitHub Actions 配置独立 PostgreSQL 18 服务调用同一完整检查。本地仓库的宿主验证与远端平台执行结果分别记录。 |

### 阶段 0–1 本地复验结果

- 在干净依赖目录运行 `pnpm install --frozen-lockfile`，退出码为 0，安装前后的锁文件摘要相同。
- `pnpm run check` 退出码为 0。格式、Lint、类型检查、52 项单元测试、1 项 HTTP 冒烟、生产构建和 2 项双实例业务验收均通过。
- 从命令行运行员工端的列表、空闲查询、预约、读取和取消，再用另一实例上的管理端查看。管理员在预约期间看到空闲区间为空，在取消后看到原时段恢复。编译产物的根路由返回 200。
- GitHub Actions 的配置随本地仓库交付。远端运行结果待首次推送后取得。

复现步骤见[本地运行与验收](booking-setup.md)。

## 阶段 2 · 实物交接

在 Node 24.22.2、pnpm 12.4.2 和 PostgreSQL 18.7 上运行。每个集成场景使用独立数据库和两个实际 API 进程。业务时间边界在测试专用数据库中固定；CLI 另使用正常数据库时钟完成交接。

| 场景               | 观测结果                                                                                                                                                                             |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 交接窗口与权限     | 开始前及结束时刻返回 `409 OUTSIDE_PICKUP_WINDOW`，开始时刻可交付。员工办理返回 403，员工读取他人的交接与读取不存在的交接均返回 404。                                                 |
| 逾期归还与提前归还 | 11:05，上一笔 10:00 至 11:00 的借还仍未归还，下一位领用得到 `409 EQUIPMENT_IN_USE`。前一笔归还后下一位成功，同设备只有新的一笔在借。另一台设备提前归还后，原预约时段仍不可重新预约。 |
| 跨进程重试         | 两名管理员分别访问不同实例，同时办理同一动作，得到相同凭据。领用、归还成功响应各丢弃一次，跨实例重试保留原经办人、时间和借还记录 ID。归还后重放领用仍返回首次领用凭据。              |
| 取消与审计         | 取消和领用争抢时只有一种变更成功。审计按顺序记录操作者、时间、前后状态。主动使审计写入失败，领用和归还均完整回滚，解除故障后可重新办理。                                             |
| 旧库升级           | 在阶段 1 迁移建成的库中预置已确认和已取消预约，再执行新迁移。原幂等键均重放原 ID。旧预约标明 `from_migration`，升级后发生的取消有独立事件。                                          |

完整检查运行 `pnpm run check`，集成测试包含阶段 0、阶段 1、阶段 2 和旧库升级四个场景。编译后的服务也通过了员工端进度查询、管理员领用、跨实例重试、归还和审计的 CLI 实测。复现命令见[本地操作指南](booking-setup.md#办理设备领用与归还)。

## 阶段 3 · 公司通知

在真实 PostgreSQL、两个 API 进程、独立 worker 与两个签名 HTTP 接收端上运行。管理员通过公开接口查询投递和重放。

| 场景               | 观测结果                                                                                                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 事务回滚与进程重启 | 在提交时强制失败，预约、审计、通知索引和发件箱行数均回到原值。随后提交成功并终止创建预约的 API，重启 worker 后仍能投递。                                                  |
| A 停机、B 正常     | A 的接收端停止期间，B 收到自己的确认。A 耗尽 5 次尝试，保留投递 ID、最近错误和尝试历史。                                                                                  |
| 先取消再重放确认   | 恢复 A 接收端后，先送达取消；代理在接收事务提交后丢弃首次应答，重试后收件箱中该事件仅一行。原确认由管理员重放成功，有五条原失败和一条新成功，公司预约仍为版本 2、已取消。 |
| 权限与指标         | 员工查询和重放返回 403，管理员并发重放同一投递恰有一个 202、一个 409。错误签名返回 401。worker 可按事件 ID 定位投递日志，并能观察到失败耗尽数量。                         |
| 旧库升级           | 用阶段 2 迁移建库并写入已有预约与审计。升级后无历史通知，首次取消只产生一条版本 2 通知。                                                                                  |

本地命令见[从预约 ID 排查并重放公司通知](notifications.md)。CI 与本地完整检查均通过 `test:booking` 的文件匹配运行上述场景。

## 阶段 4 · 滚动升级、回滚与再发布

在 2026-11-19 的 WSL Ubuntu 预发布环境中，从旧提交 `82bafe6` 升级到 `01e2712`，回滚至旧版后，再次发布相同的新版镜像。PostgreSQL 18.7、Compose 2.35.1。公开入口后有两个 API，worker 和两家公司接收端独立运行。应用、worker 和迁移任务共用各自版本的镜像。

| 验收项         | 实测结果                                                                                                                                                                                                                                          |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 持续接单       | 迁移前至再发布完成，原版客户端按原版契约发送 786 个请求。正常业务流量的 5xx、连接中断和超时均为 0。157 次预期的 409 均为 `SLOT_CONFLICT`。各持续至少一秒的阶段最低为 4.08 请求/秒，最长发起间隔 302 ms。                                          |
| 新旧共存       | 混合窗口 61.057 秒，265 个请求，平均 4.34 请求/秒。旧实例 A 收到 133 个，新实例 B 收到 132 个，两边都处理了创建、幂等重试、读取、冲突和取消。公共地点路由返回 503，定向访问新版可读到旧预约地点为 null。                                          |
| 迁移与候选失败 | 人为持锁超过 350 ms 后迁移任务失败。数据库中新增列和该迁移记录均为 0，旧版当即完成一笔预约。解除锁后依次报告应用 1 项和 0 项。另将候选 A 的数据库搜索路径指向不含业务表的 schema，直连就绪探针返回 503。候选收到 0 个用户请求，B 完成预约。       |
| 在途请求       | 摘流中的实例 B 新接会话数为 0，对端新增 5 个。慢预约 `34e9132c-88a5-46df-9f25-c80938732d17` 返回 201，库内仅一行。旧容器在 1.26 秒内退出，退出码 0，宽限期 15 秒。                                                                                |
| 契约和业务数据 | 两版均能处理旧请求，原响应通过阶段 3 的 OpenAPI 校验。管理员登记地点后，本人读到原值，另一公司员工得到 404。切回旧版后，升级期间的预约仍可读取、取消。                                                                                            |
| worker 交接    | 升级事件 `c6cf08cb-87b6-45c0-86e5-25b99a84c762`、回滚事件 `3d9d07a0-ee21-4d1f-91b3-3862a6d60e14` 均从 queued 转为 succeeded，各自沿用原事件 ID，A 公司收件箱各有一行。另逐项比对 B 公司旧通知的全部尝试和人工重放记录，升级回退与再发布后均一致。 |
| 回滚与再发布   | 从开始执行回滚到两个 API 和 worker 均恢复原镜像并就绪，用时 7.326 秒。数据库保留地点 `North lab / desk 4`。再次发布相同镜像后，本人通过公开接口读回完全相同的值。                                                                                 |

逐请求记录包含预热和停止前完成的业务循环。上表仅统计基线开始至再发布完成之间的请求；定向故障探针与人工操作另外验证。[按阶段统计、镜像 ID、预约与投递 ID](evidence/stage4.json) · [逐请求记录](evidence/stage4-traffic.jsonl) · [复现步骤](stage4-deployment.md)

另在一套全新环境逐条运行操作手册中的 CLI。升级、回滚和再发布分别用时 68.869、7.149、69.066 秒，均包含随后的状态查询。每一步的两个实例均为 `UP`，worker 与 API 镜像 ID 一致。`down --purge` 已回收该环境。

完整回归在 Node 24.22.2、pnpm 12.4.2、PostgreSQL 18.7 上运行，`pnpm run check` 退出码为 0。52 项单元测试、1 项 HTTP 冒烟、7 项 PostgreSQL 集成场景全部通过。
