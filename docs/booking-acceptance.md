# 共享设备 API 验收

## 阶段 0–1

2026-11-19 使用独立本地仓库、Node 24.22.2、pnpm 12.4.2 和 WSL Ubuntu 中的 PostgreSQL 18 容器执行。每阶段使用一个新数据库、两个实际 API 进程和公开 HTTP 客户端。

| 场景             | 核对结果                                                                                                                                            |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 空库初始化与身份 | 首次迁移应用一次，再次执行为零。重复种子后为两个组织、三个账号、两台设备。三个账号成功登录，跨实例令牌可用。错误密码、缺失和过期令牌均返回 401。    |
| 空闲查询         | 无预约返回整个窗口，时段中间已有预约则返回两段，完全占用返回空数组。等价时区输入结果一致；不同组织只收到空闲边界。                                  |
| 并发占用         | 两个客户端先看到相同时段空闲，再向不同实例并发写入。同设备重叠时段返回一个 201 和一个 409，数据库仅一笔有效预约。相邻时段及其他设备可订。           |
| 幂等与重试       | 同一员工相同键的并发重试返回同一 ID。改变时段返回 409，原时段保持有效。代理收到创建成功后丢弃响应，客户端向另一实例重试，数据库仍只有原记录。       |
| 权限与取消       | 跨组织查询和取消与不存在的记录同为 404。管理员写入为 403。重复取消均为 204；另一员工可重新预订，原键重放仍对应已取消的预约。                        |
| 契约及运行环境   | 真实客户端响应按版本化 OpenAPI 文档验证。GitHub Actions 配置独立 PostgreSQL 18 服务调用同一完整检查。本地仓库的宿主验证与远端平台执行结果分别记录。 |

### 阶段 0–1 本地复验结果

- 在干净依赖目录运行 `pnpm install --frozen-lockfile`，退出码为 0，安装前后的锁文件摘要相同。
- `pnpm run check` 退出码为 0。格式、Lint、类型检查、52 项单元测试、1 项 HTTP 冒烟、生产构建和 2 项双实例业务验收均通过。
- 从命令行运行员工端的列表、空闲查询、预约、读取和取消，再用另一实例上的管理端查看。管理员在预约期间看到空闲区间为空，在取消后看到原时段恢复。编译产物的根路由返回 200。
- GitHub Actions 的配置随本地仓库交付。远端运行结果待首次推送后取得。

复现步骤见[本地运行与验收](booking-setup.md)。

## 阶段 2 · 实物交接

在 Node 24.22.2、pnpm 12.4.2 和 PostgreSQL 18.7 上运行。每个集成场景使用独立数据库和两个实际 API 进程。业务时间边界在测试专用数据库中固定；CLI 另使用正常数据库时钟完成交接。

| 场景               | 观测结果                                                                                                                                                                             |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 交接窗口与权限     | 开始前及结束时刻返回 `409 OUTSIDE_PICKUP_WINDOW`，开始时刻可交付。员工办理返回 403，员工读取他人的交接与读取不存在的交接均返回 404。                                                 |
| 逾期归还与提前归还 | 11:05，上一笔 10:00 至 11:00 的借还仍未归还，下一位领用得到 `409 EQUIPMENT_IN_USE`。前一笔归还后下一位成功，同设备只有新的一笔在借。另一台设备提前归还后，原预约时段仍不可重新预约。 |
| 跨进程重试         | 两名管理员分别访问不同实例，同时办理同一动作，得到相同凭据。领用、归还成功响应各丢弃一次，跨实例重试保留原经办人、时间和借还记录 ID。归还后重放领用仍返回首次领用凭据。              |
| 取消与审计         | 取消和领用争抢时只有一种变更成功。审计按顺序记录操作者、时间、前后状态。主动使审计写入失败，领用和归还均完整回滚，解除故障后可重新办理。                                             |
| 旧库升级           | 在阶段 1 迁移建成的库中预置已确认和已取消预约，再执行新迁移。原幂等键均重放原 ID。旧预约标明 `from_migration`，升级后发生的取消有独立事件。                                          |

完整检查运行 `pnpm run check`，集成测试包含阶段 0、阶段 1、阶段 2 和旧库升级四个场景。编译后的服务也通过了员工端进度查询、管理员领用、跨实例重试、归还和审计的 CLI 实测。复现命令见[本地操作指南](booking-setup.md#办理设备领用与归还)。
