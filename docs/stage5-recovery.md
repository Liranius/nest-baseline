# 阶段 5 · 从最近一次在线备份恢复

员工在快照前领用了一台设备。备份完成后，A 公司收到了另一笔预约的确认，B 公司仍离线。故障前员工又成功提交了一笔预约。演练从空库恢复，验证管理员能继续归还设备，A 的重复通知只产生一次业务效果，B 能补收，并定位快照之后丢失的那笔预约。

## 复现

在 WSL Ubuntu 或 Linux 中从仓库根目录执行。使用 Git、Python 3.10+ 和 Docker Compose v2。已有阶段 4 的运行镜像时可直接执行第二条命令。首次构建需要访问镜像仓库和 npm。

```sh
python3 -B deploy/build.py 01e2712
python3 -B deploy/recovery_drill.py --output .tmp/stage5.json
```

脚本创建唯一的 Compose 项目、临时密钥和数据库卷。源库、公司的收件库、错误密钥演练库、最终恢复库分别运行在不同的 PostgreSQL 18 实例中。两个公司的接收进程沿用各自的签名密钥和收件 schema。HAProxy 入口贯穿整场；应用侧始终使用本地提交 `01e2712` 的同一镜像。

验收通过后脚本退出 0，写出脱敏 JSON，并打印 `Recovery accepted` 与恢复秒数。每次复跑可使用独立输出文件名。成功或失败均回收该项目的容器、网络、卷和临时目录；Git 中保存本次[验收结果](booking-acceptance.md)和[实测 JSON](evidence/stage5.json)。

## 备份、隔离与恢复

1. 员工和管理员通过 HTTP 准备已确认、已取消、已领用和已归还的样本。保留一条曾失败五次并由管理员重放成功的历史通知。暂停 worker，使 A、B 两条新事件保留在已提交的发件箱里。
2. 在源库打开只读、可重复读事务，导出 PostgreSQL 快照。源 API 继续提供设备查询。`pg_dump -Fc --snapshot` 使用该快照导出整个应用数据库；核对清单使用同一快照，记录预约 ID，以及每张业务表按固定顺序序列化后的行数和 SHA-256。保存归档大小、摘要、快照时刻和应用镜像 ID。[PostgreSQL 在线备份](https://www.postgresql.org/docs/18/app-pgdump.html)
3. 归档与清单位于宿主机独立私有临时目录。数据库角色由目标实例预置；数据库口令、JWT 密钥、通知加密密钥及两家公司的签名密钥保存在另一控制目录。报告仅保留标识、摘要和观测结果。接收方的数据库贯穿故障持续运行。
4. 备份后开启源 worker，等待 A 的原事件得到 204，保持 B 接收端离线。停掉源 worker，再通过 HTTP 创建标记预约。核对源端与快照的预约 ID 差集，记录源端返回的 ID 及创建审计时间。摘流后隔离源库并停止两个旧 API；此刻开始计算恢复耗时。
5. 先用损坏的归档副本测试摘要拦截，再把正确归档恢复到专用空库、故意提供错误的通知加密密钥。每次都检查公开入口为 503、worker 数为零，并比较回调观测记录，核实期间对外发送的 HTTP 请求为零。
6. 换全新卷上的空库与正确密钥，以 `pg_restore --single-transaction --exit-on-error` 恢复。逐表比对清单，并用数据库只读连接调用阶段 4 运行时检查待迁移项、原订阅、地址及解密后的签名密钥。恢复过程中不执行种子命令，也不重新配置订阅。[PostgreSQL 事务恢复](https://www.postgresql.org/docs/18/app-pgrestore.html)
7. 两个 API 均通过就绪检查后，恢复 B 接收端，启动唯一的 worker 并开放原入口。三个原账号重新登录，原有效令牌仍可使用。核对样本的预约时段、交接和审计，跨实例重试，完成归还和新预约。回调观测记录用于验证实际 HTTP 送达次数，接收库的唯一事件记录和状态行版本用于核对业务效果。

## 解读指标

- **恢复时间**从源入口完成摘流计时，覆盖两次故障注入、从新卷恢复、开放服务和最终业务验证。本地小样本目标为 300 秒。
- **快照到故障的时长**表示本次恢复的数据窗口。报告同时列出该窗口内新增后丢失的预约 ID；外部已经产生的收件效果需要按事件 ID 单独对账。
- **可追溯性**由归档 SHA-256、逐表摘要、三个集群标识、预约与事件 ID、带时间的审计及故障拒绝记录共同验证。真实归档含账号密码哈希及加密的订阅数据，演练结束后随私有临时目录清除。
